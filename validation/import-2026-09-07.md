## LDAPS regression follow-up

The failure above was a pre-connect option-readback assumption in the test.
On this Windows host, setting SecureSocketLayer=true succeeds while reading it
before connecting still returns false. The .NET Windows getter directly reads
LDAP_OPT_SSL (see [runtime source](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.DirectoryServices.Protocols/src/System/DirectoryServices/Protocols/ldap/LdapSessionOptions.Windows.cs)).

The replacement Windows test uses an ephemeral IPv4 loopback listener and anonymous
Bind to verify that the first bytes are a TLS handshake record and ClientHello.
It retains protocol/referral checks, uses bounded waits, closes the peer and
observes Bind completion. No credentials, certificate-trust changes or lab are needed.
Production TLS configuration is unchanged.

Validation: all 218 tests passed on Windows/.NET 10. A temporary mutation disabling
SecureSocketLayer made the new test fail with plaintext LDAP BER (0x30) instead
of TLS (0x16). Restoring the production code restored 218 passing tests.
This establishes TLS initiation, not a completed trusted-certificate handshake
or successful LDAPS authentication against AD; those still require integration validation.
